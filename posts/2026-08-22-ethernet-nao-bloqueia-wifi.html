Ethernet Não Bloqueia Wi‑Fi no Pi

A lembrança tinha uma origem possível, mas não explica este caso: a exclusividade entre redes é política de software opcional; aqui o rádio falha antes de existir como interface.

O que a documentação diz

A documentação oficial do Raspberry Pi trata Ethernet e Wi‑Fi como caminhos alternativos de acesso headless e também descreve cenários em que o Pi usa Ethernet enquanto hospeda uma rede sem fio. Isso não estabelece uma exclusão física entre os dois.

O Netplan permite declarar ethernets e wifis no mesmo YAML. A opção optional: true só altera a espera do boot; a documentação afirma que os endereços continuam sendo trazidos para cima. No NetworkManager, a exclusividade Ethernet/Wi‑Fi aparece como um exemplo de script dispatcher explícito que executa nmcli radio wifi off quando a Ethernet conecta.

Aplicação ao nosso Ubuntu

  • O SD tinha Ethernet e Wi‑Fi declarados juntos no network-config.
  • O Ubuntu iniciou apenas com lo e eth0; não existe wlan0.
  • O mmc1 falhou com -110 durante a inicialização SDIO, antes de qualquer associação ao SSID.
  • O Bluetooth, que compartilha o combo Broadcom, também falhou com BCM Reset failed (-110).
  • O sistema usa systemd-networkd/wpa_supplicant, não uma política NetworkManager de exclusividade.

Conclusão

Desconectar o cabo pode ser um teste complementar de primeira inicialização, mas não deve fazer aparecer um rádio que o kernel não enumerou. A lembrança é válida como armadilha de configuração em algumas imagens/políticas; a evidência deste Pi continua apontando para a falha SDIO/Broadcom onboard. A ausência de wlan0 é anterior ao problema de DHCP, prioridade ou rota.

Fontes primárias

  • Raspberry Pi — headless e redes sem fio
  • Netplan — YAML e interfaces Wi‑Fi
  • NetworkManager — exemplo explícito de exclusividade Ethernet/Wi‑Fi
