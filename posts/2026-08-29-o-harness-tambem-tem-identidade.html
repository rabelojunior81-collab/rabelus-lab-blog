O Harness Também Tem Identidade

Uma auditoria entre Codex e ZCode encontrou duas inconsistências: provider não é harness, e Git identity histórica não é evidência de runtime.

O erro que parecia pequeno

Uma sessão ZCode carregava o modelo correto, mas foi inicialmente tratada como OpenCode e depois como Codex. O problema não estava no GPT-5.6 Luna. Estava na falta de uma identidade operacional para o novo harness e na permanência de uma configuração Git de uma sessão anterior.

O que o Codex ensina

O fluxo mais maduro não depende de um hook mágico. Ele combina o bootstrap Tier 0, o Quantum Bus single-writer, eventos com proveniência, gates SAFE_CHANGE, snapshots, rollback, validadores e estados honestos. O hook é transporte; a governança vive no contrato.

O que foi alinhado

  • Um registry separa produto, harness, canal, instância, raiz do Bus, writer, Git identity e transporte de modelo.
  • O bootstrap passou a reconhecer dez arquivos canônicos e falhar quando a identidade não pode ser resolvida sem ambiguidade.
  • ZCode recebeu uma SPEC conservadora: Tier 0 obrigatório, lifecycle parcial e browser ainda NOT_VERIFIED.
  • A identidade local passou a ser argenta-full-linux-zcode, com o valor anterior preservado para rollback.

O que ainda não é claim

ZCode está instalado e seu provider foi configurado anteriormente, mas isso não prova auto-load de skills, publicação automática de eventos, compaction ou browser governado. A classificação atual é PARTIAL/NOT_VERIFIED. A próxima etapa é provar capabilities uma por vez, com consumer reread e sem alterar serviços por reflexo.

Organização é lindo: antes, durante e depois. A evidência precisa sobreviver ao harness que a produziu.
