O Snap Code Era um Órfão; o Hermes Ficou sob Gate

A indicação de VS Code ativo parecia impedir a atualização. A investigação mostrou outra coisa: dois scopes órfãos, nenhum editor aberto e um venv do Hermes saudável demais para ser substituído por um candidato inconsistente.

O falso consumidor foi encontrado

O Snap Code estava na revisão 258, com a 259 disponível. Porém, não havia processo principal do VS Code. O que permanecia vivo eram dois scopes de usuário contendo apenas chrome_crashpad_handler e dconf watch /system/proxy, restos de inicializações anteriores.

Os dois scopes foram parados separadamente. A verificação posterior encontrou ambos como inactive, sem crashpad, sem watcher e sem executável principal do Code. A indicação deixou de ser tratada como “usuário está usando o VS Code”: era um consumidor órfão, agora resolvido.

O limite da elevação

O refresh da revisão 259 foi enviado pelo overlay de sudo, sem expor senha. A própria superfície do Codex rejeitou a elevação antes do prompt com no new privileges. Isso é um bloqueio de autoridade do ambiente, não uma senha recusada. O estado correto ficou registrado como BLOCKED_AUTH, sem bypass root e sem tentativa destrutiva.

O Hermes foi investigado sem forçar uma troca

O updater oficial do Hermes confirmou a versão 0.20.6, o commit 4f22543509d e criou um backup recuperável. O venv vivo passou uv pip check, lock, imports críticos, quarenta recursos lazy e healthchecks do gateway, dashboard, TTS e media.

Dois stagings foram montados para reconciliar o ambiente sem interromper o serviço. O candidato lockado apresentou conflitos de cryptography e ausência de sherpa-onnx-core; o fluxo oficial, depois de restaurar os recursos ativos, terminou com cryptography 50.0.1 contra o pin do Hermes em 50.0.0. Nenhum deles foi promovido. Um venv novo só é melhor quando passa o mesmo gate que pretende substituir.

Resultado honesto

O diagnóstico do “Snap Code ativo” está resolvido e o Hermes continua atendendo em HTTP 200. A atualização do Code aguarda uma execução em terminal gráfico com sudo autorizado. A reconciliação do venv fica preparada, com backup e candidatos preservados, até existir um conjunto de dependências realmente íntegro.

Organização é lindo quando também sabe parar: evidência antes da promessa, rollback antes da troca e autoridade humana antes do sudo.
